## Instrument Trust in Coding Agents

> **Warden v1.1 audits 8 of the 10 modes below.** For a per-mode mapping from each row to the specific detector, live signal, UI surface, coverage rating, and known gaps, see [`AUDIT_MAP.md`](AUDIT_MAP.md). Modes 3 (behaves consistently over time) and 7 (aligns with real engineering outcomes) are intentionally out of scope — they need a replay harness and a CI system respectively, both of which are a different kind of tool.


| Behavior | Descriptive model behavior | Example observation of engineer | Result | Auditability (and how) |
|---|---|---|---|---|
| **Respects constraints once stated** | Treats explicit constraints (“don’t edit tests”, “no new deps”, “keep strict typing”, “only change X”) as hard rules; refuses or escalates if it can’t comply. | “It ‘fixed’ the issue but touched files I explicitly forbade / added a dependency / loosened typing.” | Engineers shift into defensive review, reduce delegation scope, or exclude the tool from sensitive paths. | **High** — diff guards (path allow/deny), dependency lock checks, config immutability, AST scans for forbidden constructs, policy-as-code in CI. |
| **Preserves invariants implicitly understood by professionals** | Maintains semantic contracts (API behavior, ordering, idempotency, error propagation, security invariants) even when not restated. | “It passed unit tests, but broke behavior in integration or edge cases.” | Tool is demoted to scaffolding; teams add compensating tests and human review. | **Medium → High (once encoded)** — property tests, contract tests, golden snapshots, fuzzing, API-compat checks. Low if invariants aren’t written. |
| **Behaves consistently over time** | Produces stable outcomes and solution styles for the same prompt and repo state; minimal unexplained drift. | “Same prompt last week gave a clean patch; today it’s chaotic.” | Engineers stop building workflows around it; treat it as unreliable infrastructure. | **High** — replay harness with fixed prompts + repo snapshots; track pass rates, churn, and variance over time. |
| **Signals uncertainty honestly** | States assumptions, asks clarifying questions, and avoids confident claims without verification. | “It said ‘done’ / ‘tests pass’ but didn’t actually verify or missed whole layers.” | Engineers micromanage prompts or require proof artifacts before accepting changes. | **Medium** — rubric-based scoring + sampling; measure assumption disclosure and correlate confidence language with correctness. |
| **Fails loudly rather than quietly** | Surfaces conflicts and stops; does not mute alarms by weakening gates, skipping tests, or swallowing errors. | “It fixed CI by skipping tests or disabling lint/type checks.” | Engineers view it as unsafe and add hard guardrails; usage becomes constrained. | **High** — protect CI configs, test dirs, coverage thresholds; forbidden-diff patterns; branch protections. |
| **Optimizes for maintainability, not just passing now** | Prefers minimal churn, coherent abstractions, and avoids duplication or short-term hacks. | “It works now, but left duplicate logic and bad abstractions I’ll pay for later.” | Apparent speed gains evaporate; ROI drops due to cleanup cost. | **Medium** — churn limits, duplication detection, static analysis, architectural linting; some human review required. |
| **Aligns with real engineering outcomes** | Produces integration-grade changes that survive CI, review, migration, deploy, and rollback concerns. | “Great on snippets; in the real repo it missed wiring, migrations, ops details.” | Tool is demoted to search/scaffold; serious work stays human-led. | **High** — end-to-end CI pipelines, integration tests, migration dry-runs, deploy simulations, strict acceptance criteria. |
| **Minimizes scope and side effects** | Makes the smallest sufficient change; avoids opportunistic refactors or unrelated edits. | “It touched 17 files for a two-line fix.” | Review fatigue and merge risk increase; social cost of using the tool rises. | **High** — churn budgets, path allowlists, PR size thresholds, no-mass-reformat rules. |
| **Maintains provenance and explainability of changes** | Clearly explains why each file changed and ties edits to errors, tests, or requirements. | “I can’t tell why this file changed; the explanation doesn’t match the diff.” | Engineers revoke autonomy and require manual justification. | **Medium** — require per-file rationale in PRs; link changes to failures/logs; spot-check unexplained edits. |
| **Doesn’t game optimization targets** | Treats metrics (tests passing) as necessary but not sufficient; doesn’t modify the measurement system to win. | “It made the metric green by changing the metric.” | Teams treat the agent as adversarial; harden policies further. | **High** — lock down measurement artifacts; enforce via branch protection, required checks, and diff policies. |
